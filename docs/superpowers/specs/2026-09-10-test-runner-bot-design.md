# Техническое задание: Бот для запуска автотестов (веб-сервис)

Дата: 2026-09-10

## 1. Общее назначение проекта

Веб-сервис на VPS, заменяющий/дополняющий существующий внутренний инструмент (референс — "TestFlowAI"), для запуска автотестов двумя способами:

- через **Jenkins** (триггер джобы, отслеживание статуса);
- напрямую на той же машине, где крутится бот (в том числе долгие тесты).

## 2. Технологический стек

- **Язык:** Python — тесты пишутся на Python, нужно единообразие и переиспользование кода.
- **Веб-фреймворк:** FastAPI (async, автогенерация OpenAPI, Pydantic-валидация).
- **ASGI-сервер:** uvicorn, запуск через systemd на VPS.
- **БД:** SQLite (через SQLModel/SQLAlchemy) — один файл, без отдельного сервера БД.
- **SSH-клиент:** не нужен. Все автотесты (включая тесты LLM-агентов из раздела 5) выполняются локально, subprocess'ом, на той же машине, где работает бот. Объект тестирования в разделе 5 ("Агент") — это тестируемый LLM-агент, а не удалённый хост исполнения; где физически развёрнут сам LLM-агент, ботом не управляется и его не касается.
- **HTTP-клиент:** httpx (async) — для обращения к Jenkins REST API (триггер джобы, polling статуса).
- **Очередь задач:** `asyncio.Queue` + фоновые воркеры в том же процессе, персистентность между рестартами — таблица `jobs` в SQLite с восстановлением незавершённых записей при старте.

Обоснование: нагрузка сервиса I/O-bound (ожидание Jenkins/локальных процессов), а не CPU-bound — Python с asyncio закрывает требования "быстро и мало места". Java рассматривалась и отклонена: больший расход памяти без выигрыша под этот сценарий, плюс расхождение с языком автотестов.

## 3. Структура UI

Вкладки: **Python** / **Тестирование агентов** — в скоупе этого ТЗ. **Java** / **AI Release Monitor** — вне скоупа, см. раздел 9.

### 3.1 Layout (общий паттерн для всех вкладок с запуском)

Двухколоночный layout: **сайдбар слева** — форма запуска и блок "Проверка и управление"; **центр** — список активных/недавних job'ов (чипы/табы) сверху и живой лог выбранного job'а снизу (стримится по SSE, см. раздел 6). В центральной области со временем добавятся графики/отчёты — зона зарезервирована под это расширение.

Макет согласован визуально (мокап `launch-form-v2.html` в сессии брейнсторминга).

### 3.2 Форма запуска — вкладка Python

Поля: Команда, Стенд, Тип теста, Регресс/НФ, Режим запуска (Jenkins / VM-агент), Название теста, Датасет.

Разделение по режиму запуска (Jenkins vs локальный запуск) — условные поля формы; на бэке — Pydantic-модели с discriminator по полю `execution_mode`, а не жёстко раздельные страницы.

Блок "Проверка и управление": поле ID процесса/сборки Jenkins, кнопки "Проверить" / "Перезапуск".

## 4. Фича: Управление справочниками (динамические поля форм)

### 4.1 Проблема

Значения в дропдаунах (Команда, Стенд, Тип теста и т.д.) не хардкодятся — добавление/удаление через UI без деплоя.

### 4.2 Решения по фиче

| # | Вопрос | Решение |
|---|---|---|
| 1 | Кто может редактировать | Любой пользователь, без ограничения прав |
| 2 | Какие поля редактируемые | Команда, Стенд, Тип теста, Название теста, Датасет — справочники. Регресс/НФ, execution-mode, Режим запуска (Jenkins/VM-агент) — хардкод в коде, так как влияют на логику запуска, а не просто отображаемый текст |
| 3 | Валидация при добавлении | Проверка на дубликаты значений в рамках категории |
| 4 | Удаление | Мягкое (soft delete, флаг `is_active`) — история прошлых прогонов не ломается при удалении использованного значения |
| 5 | Иерархия/зависимости | См. 4.5 ниже |
| 6 | Массовость добавления | Только точечное добавление, по одному элементу через "+" |
| 7 | Аудит изменений | Не требуется |

### 4.3 Модель данных

Единая таблица справочников `reference_items(id, category, value, is_active, sort_order)`, категории: `team`, `stand`, `test_type`, `test_name`, `dataset`.

Связи:

- `team_stand(team_id, stand_id)` — many-to-many. При создании нового Стенда сразу указывается, к каким Командам он относится (мультиселект). Управление связями — отдельная админ-панель.
- `test_name.team_id` — one-to-many (каждая Команда — свой список названий тестов).
- `dataset.test_name_id` — one-to-many (каждое Название теста — свой список датасетов).
- `test_type` — плоский список, без зависимостей.

### 4.4 Каскадное поведение формы запуска

- Смена Команды → сбрасывает Стенд и Название теста на первый доступный вариант для новой Команды.
- Смена Названия теста → сбрасывает Датасет на первый доступный вариант.

### 4.5 Важное разграничение

Справочник "Название теста" (раздел 4, общая форма запуска Python) и сущность "Тест" (раздел 5, "Тестирование агентов") — **разные вещи**, несмотря на совпадающее по смыслу название поля. Первое — плоское значение в дропдауне. Второе — полноценная сущность с путём, флагами и конструктором полей.

## 5. Фича: Страница "Тестирование агентов"

### 5.1 Иерархия сущностей

```
Команда (та же сущность, что в общем справочнике, раздел 4)
  └── Агент — тестируемый LLM-агент (несколько на одну Команду)
        └── Тест
              ├── Путь до скрипта/файла теста
              ├── Список Флагов запуска
              └── Список Полей формы (конструктор ввода)
```

### 5.2 Детали сущности "Тест"

**Путь до теста** — путь к скрипту/файлу. Фиксируется при создании/редактировании карточки Теста, не запрашивается заново при каждом запуске.

**Флаги запуска** — динамический список произвольной длины. Два типа:

- **булевый** — присутствует в команде без значения (`--verbose`);
- **со значением** — `--timeout=300`.

**Поля формы (конструктор)** — при создании/редактировании Теста задаётся список полей, которые увидит пользователь при запуске именно этого Теста. Типы поля: текст, число, выпадающий список (с заданными вариантами), чекбокс (да/нет), файл/путь (строка, без реальной загрузки файла). Каждое поле — обязательное или необязательное.

### 5.3 Связь "Поле формы" ↔ "Флаг запуска"

- У каждого поля два атрибута: **Название** (отображается пользователю) и **Имя флага** (используется в команде).
- Все поля обязательно привязаны к флагу — информационных полей без флага не бывает.
- Правила преобразования по типу поля:
  - текст/число → `--flag=значение`;
  - чекбокс отмечен → флаг подставляется как булевый (`--flag`), не отмечен → флаг не подставляется вовсе;
  - список → `--flag=выбранное_значение`;
  - файл/путь → `--flag=/путь/к/файлу`.
- **Порядок флагов** в итоговой команде — сверху вниз, в порядке заданных в конструкторе Теста полей.

### 5.4 Редактирование

Карточка Теста (путь + флаги + поля) редактируется целиком, как единая сущность.

### 5.5 Доступ

Любой пользователь может создавать/редактировать Команды, Агентов и Тесты (без ограничения прав, как в 4.2.1).

### 5.6 Итоговый принцип формирования команды запуска

```
<путь_до_теста> <флаг1[=значение1]> <флаг2[=значение2]> ... <флагN[=значениеN]>
```

### 5.7 Данные

`agent_team` = `reference_items(category=team)`. `agent(id, team_id, name)`. `agent_test(id, agent_id, path, flags_json, fields_json)`, где:

- `flags_json`: список `{name, kind: "bool"|"value", default}`;
- `fields_json`: список `{label, flag_name, type: "text"|"number"|"select"|"checkbox"|"path", required, options?}`, порядок списка = порядок в форме и в итоговой команде.

### 5.8 UI

Дерево Команда → Агент → Тест слева, карточка Теста справа: путь, таблица флагов, конструктор полей, live-превью итоговой команды. Макет согласован визуально (мокап `agent-test-constructor.html`).

После запуска — тот же паттерн вывода (список job'ов + живой лог), что и на вкладке Python (раздел 6).

## 6. Job'ы: запуск, статус, логи в реальном времени

Единая таблица `jobs(id, source: "python"|"agent_test", status, params_json, log_path, jenkins_build_id, created_at, updated_at)`. Статусы: `queued`, `running`, `success`, `failed`.

- **Локальный запуск** (VM-режим Python-вкладки и все запуски со страницы "Тестирование агентов"): бэкенд стартует subprocess, stdout/stderr пишутся в файл (`log_path`); фоновая задача tail'ит файл и стримит новые строки в браузер через **Server-Sent Events**.
- **Jenkins-режим**: триггер джобы через httpx, дальше polling статуса сборки; статус транслируется в тот же SSE-канал на UI (без файла лога либо с забором консоли джобы Jenkins — уточняется при реализации).
- UI: список активных/недавних job'ов сверху центральной колонки, живой лог выбранного job'а снизу.

## 7. Обработка ошибок

- Обязательные поля / типы значений — валидация на фронте (мгновенная обратная связь) и повторно на бэке через Pydantic (защита от прямых запросов к API, единственный источник истины).
- Дубликаты в справочниках — валидация на бэке при добавлении (раздел 4.2.3).
- Недоступность агента/хоста при локальном запуске, ошибка старта Jenkins-джобы — job уходит в статус `failed`, причина ошибки пишется в лог job'а. Отдельных алёртов/уведомлений нет.

## 8. Вне скоупа этого ТЗ

Зафиксировано явно, чтобы не потерять при дальнейшей проработке:

- **Вкладка Java** — execution-mode, номер тикета (UNAPOLLO), сверка веток. Поля и логика не проработаны.
- **Вкладка AI Release Monitor** — не описана вообще, требует отдельного брейнштормингa.
- **Права доступа / аутентификация** — сейчас сознательно без ограничений (см. 4.2.1, 5.5); может понадобиться пересмотр при выходе за пределы внутреннего использования.
- Иерархия/зависимости для "Тип теста" — сейчас плоский список, зависимость от Команды/Стенда не нужна (см. 4.5, 5.1 отличие от `test_name`).
