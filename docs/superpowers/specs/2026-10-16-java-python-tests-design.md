# Раздельные Java- и Python-тесты с произвольными параметрами

## Зачем

Сейчас тесты в справочнике общие для Java и Python: категория `test_name` привязана только к команде,
у теста одно поле `command`. Один и тот же тест виден на обеих вкладках, но у Java и Python
разные имена тестов, команды и параметры. Признак «фронт/бэк» есть только в форме запуска Java,
у самих тестов его нет, и список тестов по нему не фильтруется. Добавлять тест неудобно:
форма идёт строкой внизу плитки.

## Цели

1. Java-тесты и Python-тесты — разные сущности, у каждой своя плитка в «Справочниках».
2. У Java-теста обязательная «Часть»: фронт или бэк.
3. У любого теста есть произвольные параметры: пары «ключ = значение», где значение может быть пустым.
   Параметры фиксируются при создании теста и уходят в запуск как есть.
4. Тест создаётся и редактируется в модальном окне по центру (вариант A из макета: одна колонка;
   сверху основные поля, ниже строки параметров «ключ | значение | ✕» и «+ параметр»).
5. На вкладке Java появляется выбор «Режим: многопоточный / однопоточный», он уходит в Jenkins.
6. Датасеты привязываются только к Python-тестам.

## Не цели

- Миграции и перенос старых тестов. Пользователь сам удалит `test_runner.db`.
- Заполнение параметров при запуске: значения задаются только в справочнике.
- Изменения в «Тестировании агентов» (`Agent`/`AgentTest`).
- Отслеживание Jenkins-сборок и аутентификация (намеренно отсутствуют).

## Анти-цели

- Тест одного языка не должен попадать на вкладку другого языка.
- Параметр теста не должен молча перезаписывать служебный параметр запуска (команда, стенд и т. п.).

## Решения

### Модель (`app/models/reference.py`)

- Категория `test_name` удаляется, вместо неё появляются `java_test` и `python_test`. Родитель обеих — `team`.
  Родитель `dataset` теперь `python_test`.
- В `ReferenceItem` добавляются колонки:
  - `part: str | None` — `"front" | "back"`, обязательна у `java_test` и равна `None` у остальных категорий;
  - `params_json: str | None` — JSON-список `[{"key": str, "value": str | null}, …]`, порядок сохраняется.
- Хелпер `test_params(item) -> list[dict]`: разбирает `params_json`, для `None` возвращает пустой список.
- `launch_reference_error` получает категорию теста (`java_test` / `python_test`) и необязательный `part`.
  Тест должен быть активным, нужной категории, принадлежать команде, а для Java ещё и иметь ту же часть
  («Тест не найден у этой команды и части — обновите страницу»). Датасет должен принадлежать `python_test`.

### API справочников (`app/routers/references.py`)

- `Category = Literal["team", "stand", "java_test", "python_test", "dataset"]`, обновить `PARENT_CATEGORY`.
- Запросы create/update принимают `part: Literal["front","back"] | None` и
  `params: list[{key, value}]` (по умолчанию `[]`).
- Валидация (422, сообщение на русском):
  - `part` обязателен у `java_test` и запрещён у остальных категорий; `params` разрешены только у `*_test`;
  - ключ — непустая строка по `^[A-Za-z0-9_][A-Za-z0-9_.-]*$` (подходит и для имени параметра Jenkins, и для флага);
  - ключи внутри теста не повторяются;
  - ключ не совпадает со служебным именем языка (см. «Запуск»), сравнение без учёта регистра; у Python-теста
    ключ также не может быть префиксом VM-флага (`tea` → argparse с `allow_abbrev` развернёт `--tea` в `--team`).
    Списки служебных имён лежат в одном модуле, который используют и API справочников, и роутеры запуска.
    Проверка выполняется только при сохранении *(решение исполнителя)*;
  - пустое или пробельное значение сохраняется как `null`.
- Проверка дубля (409) в create и update учитывает `part`: у одной команды допустимы `login`/фронт и `login`/бэк.
- Ответ `ReferenceItem` содержит `part` и `params_json`, а фронт разбирает их сам. Приемлемо также
  вернуть разобранное поле `params`, на усмотрение исполнителя.
- Фрагменты `<option>`:
  - `GET /fragments/java-tests?team_id=&part=` — активные `java_test` команды с этой частью;
  - `GET /fragments/python-tests?team_id=` — активные `python_test` команды;
  - `GET /fragments/datasets?test_id=` — родитель должен быть `python_test`;
  - старый `/fragments/test-names` удаляется. Правила для пустого и отсутствующего родителя такие же, как сейчас
    (пустой → пустой список, отсутствующий → 422). Для `part` действует то же правило.

### Страница «Справочники» (`references.html`)

- Плитка «Имена тестов» заменяется двумя: **«Java-тесты»** и **«Python-тесты»**. Группировка по команде
  и «сироты» под «Без команды» остаются как сейчас, отдельно в каждой плитке.
- Строка теста показывает имя, `· <code>команда</code>`, у Java бейдж «Фронт»/«Бэк» и число параметров.
- Под каждой плиткой кнопка «+ Добавить Java-тест» / «+ Добавить Python-тест» вместо inline-формы.
- Одно модальное окно `#test-modal` (те же классы `modal-overlay`/`modal-dialog`, что у стенда)
  работает в двух режимах:
  - создание: категория берётся из кнопки, поле «Часть» (радио «Фронт»/«Бэк», по умолчанию фронт)
    показывается только для Java;
  - редактирование: кнопка ✎ у строки теста открывает окно с заполненными полями и делает `PUT`.
    Inline-редактирование у тестов больше не используется, у остальных категорий остаётся.
- Поля окна: команда (select), имя теста, команда запуска, [часть], параметры. «+ параметр»
  добавляет строку из двух input (ключ, значение с placeholder «без значения») и ✕. Полностью пустые
  строки при сохранении отбрасываются.
- Ошибки API показываются через `formError` в теле окна. Esc и клик по фону закрывают окно.
- В форме датасета список тестов содержит только `python_test`. Плитка датасетов группирует по Python-тестам.

### Запуск Java (`launch_java.py`, `java_tab.html`)

- Новое поле формы `thread_mode: Literal["multi","single"]` — select «Режим»: «Многопоточный» / «Однопоточный».
- Селект теста грузится из `/fragments/java-tests` с `hx-include` команды и части и перезагружается
  при смене любой из них. Поле формы называется `test_id`.
- В Jenkins уходят: `team_id, stand_id, regression_type, part, thread_mode, test_name_id, test_command`
  (имена прежние, чтобы не ломать джобу; `None` отбрасываются), затем параметры теста. Ключ без
  значения уходит как `key=` (пустая строка).
- Служебные ключи Java = имена из списка выше.
- В `Job.params_json` записываются также `thread_mode` и `test_params`.

### Запуск Python (`launch_python.py`, `python_tab.html`)

- Селект теста грузится из `/fragments/python-tests`, датасеты — из `/fragments/datasets?test_id=`.
- VM: после нынешних аргументов дописываются параметры теста, `--key=value` или голый `--key`,
  если значения нет. Расширить `build_command` или дописывать в argv после него — на усмотрение исполнителя.
- Jenkins: нынешние параметры, затем параметры теста по правилам Java (`key=` для пустого значения).
- В `Job.params_json` записывается и `test_params` (так же, как у Java).
- Попутный баг: в `PYTHON_FIELDS` поле `--test-name` объявлено `type="number"`, а получает строку команды,
  поэтому `build_command` падает с `ValueError` → 500, хотя Job уже сохранён как `queued`. Нужно поменять тип на `text`.
- Служебные ключи Python = имена Jenkins-параметров (`team_id, stand_id, regression_type, test_name_id,
  test_command, dataset_id`) плюс имена VM-флагов без `--` (`team, stand, regression-type, test-name, dataset`).

### Тесты

Обновить `test_reference_api.py`, `test_launch_java_api.py`, `test_jobs_api.py` (Python-запуск) под новые
категории. Новые проверки: валидация part и params, фильтр по части, изоляция языков (Java-тест не принимается
Python-запуском и наоборот), argv с параметрами (с значением и без), Jenkins-параметры с `thread_mode`
и параметрами теста, отказ при служебном ключе, датасет только у python_test. Шаблоны проверяются по тексту
(есть `#test-modal`, обе плитки).

## Оставлено исполнителю

Разметка и стили окна в рамках существующих классов, имена JS-функций, разбиение на коммиты,
форма ответа API для params (сырой JSON или разобранный список).
